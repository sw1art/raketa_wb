# 5. Функциональные требования

## 5.1. Каталог товаров

Реализовать:
- создание товара;
- редактирование товара;
- просмотр списка товаров;
- получение информации о товаре;
- привязку товара к магазину;
- хранение внутреннего SKU;
- хранение внешнего идентификатора Wildberries, если он известен.

Тестовые товары:

| SKU | Название |
|---|---|
| SKU-101 | Органайзер |
| SKU-102 | Контейнер |
| SKU-103 | Корзина |

Не допускать дублирования SKU в рамках одного магазина.

## 5.2. Управление складами

Реализовать:
- создание ФФ;
- просмотр списка ФФ;
- редактирование названия;
- просмотр остатков конкретного ФФ;
- архивирование ФФ.

Начальные склады:
- Север;
- Юг.

Удаление должно быть логическим.

Использовать статус или признак активности склада.

Правила:
- нельзя архивировать склад с ненулевыми физическими остатками;
- нельзя архивировать склад с незавершёнными перемещениями;
- нельзя архивировать склад, пока существуют незавершённые операции, связанные с ним;
- после архивирования история операций должна сохраняться;
- архивированный склад не должен использоваться в новых операциях.

При попытке архивирования склада с остатками возвращать понятную ошибку с указанием товаров и количества.

## 5.3. Складские остатки

Для каждого SKU и ФФ хранить:
- физическое количество;
- зарезервированное количество;
- доступное количество.

Формула:

Available = Physical - Reserved

Где:
- Physical — фактическое количество товара на ФФ;
- Reserved — количество товара, зарезервированное под FBS;
- Available — количество, доступное для новых операций.

Обязательно обеспечить:
- Physical >= 0;
- Reserved >= 0;
- Reserved <= Physical;
- Available >= 0.

Товары в пути не должны входить в физические остатки ФФ.

Для товаров в пути предусмотреть отдельный механизм учёта.

Не смешивать:
- физические остатки ФФ;
- резервы FBS;
- внутренние перемещения;
- отправки FBO;
- отправки FBS.

## 5.4. Начальные остатки

Заполнить систему тестовыми данными:

| SKU | Товар | Север | Юг |
|---|---|---:|---:|
| SKU-101 | Органайзер | 10 | 6 |
| SKU-102 | Контейнер | 5 | 0 |
| SKU-103 | Корзина | 0 | 4 |

Реализовать механизм начального заполнения через seed-скрипт.

Seed должен быть идемпотентным: повторный запуск не должен дублировать товары, склады и остатки.

## 5.5. Приход товара

Use Case: ReceiveStockUseCase.

Сценарий:
1. Выбрать ФФ.
2. Выбрать SKU.
3. Указать количество.
4. Проверить корректность входных данных.
5. Увеличить физический остаток.
6. Создать операцию.
7. Создать запись складского движения.
8. Записать Domain Event.
9. Сохранить Outbox Event в той же транзакции.

Событие: StockReceived.

## 5.6. Резервирование FBS

Use Case: ReserveFBSStockUseCase.

Сценарий:
1. Выбрать товар.
2. Выбрать ФФ.
3. Указать количество.
4. Проверить доступность.
5. Создать резерв.
6. Увеличить Reserved.
7. Не изменять Physical.
8. Создать историю операции.
9. Сохранить событие в Outbox.

Если доступного количества недостаточно, операция должна быть отклонена.

Событие: StockReserved.

## 5.7. Отмена резерва FBS

Use Case: CancelFBSReservationUseCase.

Сценарий:
1. Найти резерв.
2. Проверить его статус.
3. Убедиться, что он ещё не отправлен.
4. Перевести резерв в CANCELLED.
5. Освободить зарезервированное количество.
6. Сохранить историю.
7. Создать событие.

Физический остаток при отмене резерва не меняется.

Событие: StockReservationCancelled.

## 5.8. Отправка FBS

Use Case: ShipFBSOrderUseCase.

Сценарий:
1. Найти активный резерв.
2. Проверить статус резерва.
3. Проверить доступность подтверждения.
4. Уменьшить Physical.
5. Освободить Reserved.
6. Изменить статус резерва.
7. Создать отправку.
8. Сохранить складское движение.
9. Сохранить историю.
10. Записать событие в Outbox.

Пример:

До отправки:

Physical = 20
Reserved = 5
Available = 15

После отправки 5 единиц:

Physical = 15
Reserved = 0
Available = 15

Повторная отправка одного резерва не должна повторно списывать товар.

Событие: FBSOrderShipped.

## 5.9. Перемещение между ФФ

Реализовать двухэтапное перемещение.

Use Cases:
- CreateTransferUseCase;
- DispatchTransferUseCase;
- ReceiveTransferUseCase.

### Создание перемещения

- выбрать исходный ФФ;
- выбрать целевой ФФ;
- выбрать SKU;
- указать количество;
- проверить доступный остаток;
- создать перемещение.

### Отправка

При подтверждении отправки:
- проверить статус;
- заблокировать конкурентное изменение соответствующего остатка;
- уменьшить Physical исходного ФФ;
- создать запись о товаре в пути;
- изменить статус на IN_TRANSIT;
- сохранить историю;
- записать событие в Outbox.

### Приёмка

При подтверждении приёмки:
- проверить статус IN_TRANSIT;
- увеличить Physical целевого ФФ;
- закрыть запись о товаре в пути;
- изменить статус на RECEIVED;
- сохранить историю;
- записать событие.

Повторная приёмка должна быть невозможна.

## 5.10. Отправка FBO

Реализовать отправку товара на склад Wildberries.

Use Cases:
- CreateFBOShipmentUseCase;
- DispatchFBOShipmentUseCase;
- ReceiveFBOShipmentUseCase.

Сценарий:
1. Выбрать исходный ФФ.
2. Выбрать SKU.
3. Указать количество.
4. Проверить доступный остаток.
5. Создать отправку.
6. При подтверждении отправки уменьшить физический остаток ФФ.
7. Перевести товар в состояние IN_TRANSIT.
8. При приёмке на WB перевести отправку в RECEIVED.
9. Сохранить всю историю.

Товар в пути учитывается отдельно.

Внешний статус WB и внутренний статус отправки должны храниться отдельно, если они имеют разные значения.

## 5.11. Обработка нехватки товара

Обязательный сценарий.

Пример:

| Склад | SKU-101 |
|---|---:|
| Север | 2 |
| Юг | 10 |

Менеджер пытается отправить 5 единиц с Севера.

Система должна:
1. Обнаружить нехватку.
2. Отклонить операцию.
3. Показать доступный остаток на других ФФ.
4. Рассчитать недостающее количество.
5. Предложить перемещение товара.
6. Не выполнять автоматическое списание с другого ФФ.

Система не должна допускать отрицательных остатков.

# 7. Транзакционность и конкурентный доступ

Это критически важный раздел.

Любая операция, изменяющая складской баланс, должна выполняться в одной транзакции PostgreSQL.

Нельзя допускать ситуацию, когда:
- остаток изменён, но операция не записана;
- операция записана, но остаток не изменён;
- событие не сохранено после успешного изменения остатков;
- два параллельных запроса списывают одни и те же товары.

Использовать подходящий механизм блокировки:
- SELECT FOR UPDATE;
- либо атомарные UPDATE с условием достаточного остатка.

При необходимости использовать optimistic locking через version.

Для каждой операции определить чёткую границу транзакции.

Не выполнять сетевые запросы к RabbitMQ или Wildberries внутри длительной транзакции складской операции.

# 8. Outbox Pattern и Event-Driven Architecture

Обязательно реализовать Transactional Outbox Pattern.

## 8.1. Общий принцип

При выполнении складской операции в одной транзакции PostgreSQL должны:
1. Измениться складские остатки.
2. Создаться запись операции.
3. Создаться складские движения.
4. Создаться запись Outbox Event.

Если транзакция откатилась, все изменения должны откатиться вместе.

## 8.2. Таблица Outbox

Минимальные поля:
- id;
- event_id;
- aggregate_type;
- aggregate_id;
- event_type;
- payload;
- status;
- created_at;
- published_at;
- retry_count;
- last_error.

Статусы:
- PENDING;
- PUBLISHED;
- FAILED.

## 8.3. Outbox Publisher

Реализовать отдельный фоновый процесс.

Его задачи:
1. Находить неопубликованные события.
2. Безопасно захватывать события для обработки.
3. Публиковать их в RabbitMQ.
4. Подтверждать успешную публикацию.
5. Повторять публикацию после временных ошибок.
6. Сохранять информацию об ошибках.
7. Не допускать потери событий.

Предусмотреть корректную работу нескольких экземпляров Publisher, например через FOR UPDATE SKIP LOCKED.

Не отмечать событие опубликованным до получения подтверждения RabbitMQ Publisher Confirm.

## 8.4. RabbitMQ

Использовать:
- Durable Exchange;
- Durable Queues;
- Routing Keys;
- Publisher Confirms;
- Manual Acknowledgements;
- обработку повторных доставок;
- Dead Letter Queue для неисправимых ошибок.

Предусмотреть версионирование событий.

Пример событий:
- StockReceived;
- StockReserved;
- StockReservationCancelled;
- FBSOrderShipped;
- FBOShipmentDispatched;
- FBOShipmentReceived;
- TransferDispatched;
- TransferReceived;
- WarehouseArchived.

## 8.5. Consumers

Реализовать минимум один полноценный Consumer, например для формирования событийного журнала или обработки вторичных уведомлений.

Все Consumers должны быть идемпотентными.

Использовать processed_events с уникальным ограничением по consumer_name + event_id.

Обеспечить безопасную повторную доставку сообщений.

Важно: RabbitMQ используется для распространения событий, а не как источник истины для складских остатков.
